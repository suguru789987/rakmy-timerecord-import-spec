## 概要

ラクミータイムレコードの設定データ(従業員、雇用区分、店舗、業態)を外部からインポートする機能の仕様書。

### インポート方式

| 方式 | 対象ユーザー | 特徴 | 実装フェーズ |
|---|---|---|---|
| **テンプレートインポート** | 全ユーザー | ラクミー指定テンプレートにデータを入力してインポート | **先行実装（本仕様の主対象）** |
| 外部勤怠サービスインポート | KoT/Jobcanユーザー | CSVエクスポートデータを列マッピングしてインポート | **⛔ 凍結（仕様未完成・担当不在）** |

### 実装フェーズと仕様の正本（2026-07-28 確定）

**テンプレートインポートを先行実装し、外部勤怠サービスインポートは後続とする。**

- **仕様の正本はテンプレートインポート側（§1）。** §7〜§9 の決定事項は、まずテンプレートインポートに対して適用する
- **§2 外部勤怠サービスインポートは後続実装。** マッピング表（`設定データインポートマッピング表.tsv`）を含め、後続フェーズで §1 の確定内容に追随させる。先行フェーズでは仕様を凍結する
- モックには両方式の画面が入っているが、**先行実装の対象はテンプレート側の画面のみ**（`s-tpl*` 系）。外部勤怠側（`s-saas*` 系）は後続フェーズの参照用

**各決定事項の「適用範囲」ラベル（語彙は次の4つに固定）**

| ラベル | 意味 | 判断基準 |
|---|---|---|
| `テンプレートのみ（先行実装）` | テンプレートインポートにのみ適用 | テンプレートの列定義・ファイル配布に起因するもの |
| `外部勤怠のみ（後続実装）` | 外部勤怠サービスインポートにのみ適用 | 列マッピング・外部サービスのエクスポートに起因するもの |
| `両方式共通` | 両方に適用 | DB制約・API仕様・画面挙動に起因するもの |
| `方式別に定義済み` | 方式ごとに要件が異なり、それぞれ定義済み | 現状は §9.5（文字コードの扱い）のみ |

§7.1〜§9.7 の全小節と、§1／§3／§4.1／§4.2／§4.3／§5 の章冒頭に必ず記載する。`audit_spec_mock.py` が網羅と語彙を機械的に検査する。

**ラクミー側の許可値は、実装（DBのenum）を正とする**

外部サービスの語彙をそのままラクミー側の許可値に写してはならない。

- 実例: 給与体系の「日給」は、KoT人事労務の `個人.契約種別` と Jobcan給与計算の `給与形態` が取りうる値（月給/日給/時給）をそのまま許可値として採用したもので、**タイムレコード本体は `pgEnum("employment_category", ["時給","月給"])` の2値**だった（§8.10）
- マッピング表は外部サービス起点で書かれているため、「**外部サービス側の値**」と「**ラクミー側の許可値**」は別物として扱う。後者は必ずアプリ側の実装で裏を取る
- 後続フェーズでマッピング表に列を足す際も、このルールを適用する

`main`（2026-07-13）および `develop` には**未マージ**で、`stores.business_hours`（`0009_stores_business_hours.sql`）などが存在しない。**`main` と照合すると §7.3 が誤りに見える**ため、確認時は必ずブランチを合わせること。

### 0.2 実装フェーズ

**実装対象はテンプレートインポート（§1）のみ。** 外部勤怠サービスインポート（§2）は**仕様未完成のまま凍結**（2026-07-31）。仕様を維持する担当が不在のため開発を進められない。

> ⚠️ **実装対象はモックの `s-tpl*` 系画面のみ。** `s-saas*` 系（および補完画面 `s-tpl-complete`）は**凍結中で実装対象ではない**。

### 0.3 ロール区分 — 管理者（全権・店長）と従業員の2区分のみ

```
src/db/schema/enums.ts
export const roleEnum = pgEnum("role", ["owner", "manager", "employee"]);
```

| 区分 | ロール | 店舗の範囲 |
|---|---|---|
| 管理者（全権） | `owner` | 全店舗。担当店舗という概念を持たない |
| 管理者（店長） | `manager` | 自分の店舗。**勤務店舗と一致する** |
| 従業員 | `employee` | 勤務店舗 |

- **「管理するが勤務しない」役割（エリア長・本部管理者など）は存在しない。** カスタム権限も作れない
- **⑤管理者テンプレートで登録できるのは店長（`manager`）のみ。** 全権（`owner`）はセルフサインアップ時にのみ生成され、管理者登録APIに role フィールドがない（§7.4）
- ラクミー**経営管理**の権限設定（`master` / `manager` / `shop_manager` ＋カスタム権限、「権限は権限、範囲は割当」）とは**別プロダクトの別モデル**。混同しないこと

### 0.4 店舗割当は単一テーブル

勤務店舗も担当店舗も `userStoreAssignments`（複合主キー `user_id, store_id`）で持つ。0.3 のとおり両者が一致する役割設計のため、**この設計は正しい**。テーブル分離は不採用（§7.1）。

管理者登録APIは `storeIds` を**全件置換**で処理する（`delete` → `insert`）。詳細と対処は §7.1。

### 0.5 給与体系は時給・月給の2値

```
src/db/schema/enums.ts:8
export const employmentCategoryEnum = pgEnum("employment_category", ["時給", "月給"]);
```

日給は存在しない。詳細は §8.10。

### 0.6 コードは全社横断でユニーク／自動採番は既存実装あり

`users.employee_code` と `employment_types.employee_code` は `company_id` との複合ではなく**テーブル全体でユニーク**。自動採番は `EMP-{5桁のランダム数字}` がアプリ側に実装済み（`src/app/api/employees/route.ts:286-303`）。詳細は §8.1。

### 0.7 守るべき制約はDB側のみ。それ以外は実装の選択

**登録の経路は2つ。** テンプレートインポート登録（外部勤怠インポートは後続）と、手入力設定登録（画面から1件ずつ）。

**インポートが手入力の登録処理を再利用するかどうかは実装の選択であり、仕様ではない。** サーバー側でDBへ直接書く作りも取り得る。したがって、**どう実装しても回避できないDB側の制約だけが仕様の前提**となる。

| 種類 | 内容 |
|---|---|
| enum | 給与体系 `["時給","月給"]` ／ 交通費単位 `["日額","月額"]` ／ ロール `["owner","manager","employee"]` ／ 在籍状況 `["active","inactive","retired","inviting"]` |
| ユニーク制約 | `users.employee_code` ／ `employment_types.employee_code`（いずれも**全社横断**） |
| NOT NULL | `stores.name` ／ `stores.business_type_id` ／ `employment_types.name` `category` `rate` `employee_code` ／ `users.employee_code` `name` `email` ほか |
| 型と桁 | `varchar(255)`（従業員名・店舗名・メール）／ `varchar(100)`（雇用区分名・業態名）／ `varchar(50)`（各コード）／ `varchar(20)`（電話番号）／ `decimal(10,2)`（金額）／ `integer`（月次契約労働時間）／ `text`（住所・営業時間・月みなし残業時間） |

> ⚠️ **手入力経路の入力検証（zodスキーマ）は、DBの制約とは別物。** 例えば従業員名はDBが `varchar(255)` に対し、手入力経路の `createEmployeeSchema` は `max(100)`。**インポートがその経路を再利用しない場合、100文字の制限は適用されない。**
>
> 本仕様で「実効上限」「1行あたり◯リクエスト」「置換される」と書いている箇所は、**手入力経路を再利用した場合の話**であり、その旨を各所に明記している。再利用するかどうかは §11 で決める。

### 0.8 バッチのトランザクションが張れない

`neon-http` ドライバは `db.transaction()` 非対応。途中で失敗してもロールバックできない。失敗ハンドリングは §7.7。

## 4. 内部仕分けロジック

### 4.1 テンプレートインポート時


> **適用範囲: テンプレートのみ（先行実装）**

各テンプレートを順番に登録（5ファイル・エンティティ別なので結合ファイルの自動仕分けは不要）:

| 処理順 | テンプレート | ロジック |
|---|---|---|
| 1 | ① 業態 | 全行登録 |
| 2 | ② 店舗 | 全行登録、所属業態で①に紐付け |
| 3 | ③ 雇用区分 | 全行登録（雇用区分コードは空欄時自動生成） |
| 4 | ④ 従業員 | 全行登録、雇用区分名・店舗名で③②に紐付け |
| 5 | ⑤ 管理者（任意） | 全行登録、担当店舗で②に紐付け、招待メール送信 |

### 4.2 外部SaaSインポート時


> **適用範囲: 外部勤怠のみ（後続実装）**

2つのデータソース選択時の統合ロジック:
- 1st（設定データ）をベースにレコード作成
- 2nd（給与データ）を従業員コードをキーに補完・統合
- 2ndにしかない列（給与体系、通勤手当等）を1stのレコードにマージ

### 4.3 重複時の処理


> **適用範囲: 両方式共通** — 突合ロジックに起因するため。

| 設定 | 動作 |
|---|---|
| スキップ（既存を保持） | 同一キーのレコードが存在する場合、既存データを変更しない |
| 上書き更新 | 同一キーのレコードが存在する場合、新しいデータで上書き |

ユニークキー:
- 従業員: 従業員コード（システムID）
- 雇用区分: 雇用区分コード（空欄時は雇用区分名 → §8.6）
- 店舗: 店舗名
- 業態: 業態名

### 7.1 管理者データの判定ラベル（5分岐）

> **適用範囲: テンプレートのみ（先行実装）** — 管理者は⑤テンプレート専用。外部連携では管理者を取り込まない（§7.6）

プレビュー画面の「判定」列に出す確定ラベルと定義。突合は必ず **`companyId` で絞った会社内のメールアドレス突合**で行う。メールアドレスは全社ユニークではない（`users.emailIdx` は非ユニークインデックス）ため、全社横断で突合すると他社ユーザーを誤判定する。

- **新規登録** — 同じメールアドレスのユーザーが会社内に存在しない。ユーザーを新規作成し管理者権限を付与。招待メール（新規版）を送信
- **権限付与** — 従業員として在籍済み・招待承諾済み・まだ管理者ではない。既存ユーザーに管理者権限を追加（昇格）し、ユーザーは新規作成しない。管理者権限付与のお知らせを送信
- **差し替え** — 招待済みだが未承諾（status = inviting）。旧招待を無効化して招待を再発行。【再送・差し替え】招待メールを送信
- **スキップ** — すでに管理者権限を持っている。何もしない。メール送信なし
- **エラー** — 必須項目不足／担当店舗が未登録／メールアドレス形式不正 など。取り込まない。メール送信なし

実装側の `users.adminInvitationType`（`'new'` / `'promoted'`）、管理者登録APIの `mode: "new"` / `mode: "promote"`、および3種の送信関数（`sendAdminInvitationEmailNew` / `sendAdminPromotionNoticeEmail` / `sendAdminInvitationReplacementEmail`）と1対1で対応する。

**「既存登録」と「差し替え」の切り分け基準は「招待を承諾済みか未承諾か」。** 承諾済みなら権限付与、未承諾なら差し替え。

**担当店舗（`storeIds`）の扱い（2026-07-28 確定）**

⑤管理者テンプレートの「担当店舗」は `storeIds`（**1件以上必須**）としてAPIに渡る。アプリ側は `userStoreAssignments` を**追加ではなく置換**する（`delete` してから `insert`）。`promoteActiveEmployee` / `promoteInvitingEmployee` の**両方**で確認済み。

**仕様として守るべきことは1つ。「既存従業員を管理者に昇格させても、その従業員の勤務店舗を失わせない」。** 以下は手入力経路の登録処理を再利用する場合の具体化である（§0.7・§11）。DBへ直接書く実装なら、そもそも消さないように書けばよい。

そのままだと **CSVに書かれていない既存の勤務店舗が削除される**。渋谷店・新宿店で勤務する従業員を担当店舗「渋谷店」だけで昇格させると、新宿店の所属が消えて打刻できなくなる。画面の「従業員から選択」タブは所属店舗を初期チェックした状態で開くためこの事故が起きにくいが、**CSVには初期チェックに相当する仕組みがない**。

**決定：取り込み時に `storeIds` を「CSVの担当店舗 ∪ その従業員の既存の所属店舗」とする。選択肢は設けない。**

- **対象は「権限付与」「差し替え」の行のみ。** どちらも既存ユーザーに対する操作で `storeIds` を受け取る。「新規登録」は既存の所属店舗が存在せず、「スキップ」「エラー」は取り込まないため対象外
- **利用者に選ばせない理由**（当初はチェックボックス案だったが不採用）
  1. ⑤で登録できるのは**店長（`manager`）のみ**。全権（`owner`）はセルフサインアップ時にのみ生成され、管理者登録APIに role フィールドがない（§7.4）
  2. **店長の担当店舗は勤務店舗と一致する。** タイムレコードのセルフ機能に「管理するが勤務しない」役割（エリア長・本部管理者など）は存在せず、区分は管理者（全権・店長）と従業員の2つのみ
  3. 担当店舗を減らしたいのは既存管理者だが、その行は「スキップ」となり**何も実行されない**（⑤テンプレートでは既存管理者の担当店舗を変更できない。変更は画面から）
  4. 以上より**オフにする場面が存在しない**。押す理由のない選択肢を見せないため、常時適用とする
- プレビューは判定のためにメール突合で対象ユーザーを特定済みのため、その `userStoreAssignments` を引けば既存の所属店舗を表示できる。マージ結果をそのまま表示する
  > `担当店舗: 渋谷店, 新宿店 (新宿店は既存の勤務店舗)`

> **§8.3 との関係**: ④従業員で「複数店舗は取込後に画面から追加」とした運用と衝突しうる。画面で追加した所属店舗も、⑤で昇格させる際に担当店舗へ書き漏らせば消える。**常時マージによりこの衝突を構造的に回避する。**

> **勤務店舗と担当店舗をテーブル分離する案は不採用（2026-07-28 判断）。** 分離が要るのは「管理するが勤務しない」役割が存在する場合だが、本製品の区分は管理者（全権・店長）と従業員の2つのみで該当しない。全権は全店舗が対象で担当店舗の概念を持たず、店長の担当店舗は勤務店舗と一致する。`userStoreAssignments` を単一テーブルで持つ現行設計はこの役割設計に対して正しい。将来この前提が変わった場合のみ再検討する（`userStoreAssignments` の参照は80箇所/19ファイルで、打刻・権限チェックを含む）。

**「判定の見方」は既定で折りたたむ（2026-07-28 追記）**

5分岐の凡例は**常時表示せず、`<details>` で閉じた状態を既定**とする。summary は `判定の見方（5分岐の説明 — 必要なときに開いてください）`。

- 判定ラベル自体は各行のバッジで色分けされており、**凡例を常に開いておく必要はない**。常時表示すると「重複時の処理」など実際に操作する要素より縦幅を取り、プレビュー表から視線が逸れる
- 凡例が必要なのは初回利用時と、見慣れないラベル（差し替え等）が出たときに限られる
- 実装箇所: `details.legend-details`（⑤管理者のプレビュー2画面）

**用語の注意:** 「マスタ登録済み」という表現は使わない。「マスタ」は ①業態／②店舗／③雇用区分 を指す語として使っているため、従業員の意味で使うと衝突する。「従業員として登録済み」に統一する。

**スキップはエラーではない:** 「すでに管理者」は不備のない正常系のため、エラー件数には含めずグレーの独立枠でカウントする。エラー枠に混ぜると「エラー行を除いてインポート実行」ボタンとの関係でユーザーが混乱する。

### 7.2 プレビュー各タブの表示ルール

> **適用範囲: 両方式共通** — どちらのプレビュー画面にも適用する

**タブの軸はデータ種別ごとに異なる（2026-07-28 追記）**

同じ「タブ」に見えるが、①〜③と④⑤で担っている軸が違う。**混在させてはならない。**

| 対象 | タブの軸 | 内容 |
|---|---|---|
| ①〜③ 設定マスタ | **データ種別** | `業態 (2)` / `店舗 (2)` / `雇用区分 (3)` |
| ④ 従業員 | **行ステータス** | `すべて (8)` / `エラー (1)` |
| ⑤ 管理者 | **行ステータス** | `すべて (6)` / `差し替え (1)` / `スキップ (1)` / `エラー (1)` |

- **①〜③に「すべて」「エラー」タブは追加しない。** ①〜③は1画面に3つのマスタが同居するためタブ行を種別切替に使い切っている。ここにステータス軸を足すと1本のタブ行に2軸が混在し、「業態」と「エラー」が横に並ぶ形になって何の切替か分からなくなる
- **①〜③のエラーは、タブではなく次の3点で表示する**（実装例: `s-tpl2` の「①〜③ 設定マスタ」→「店舗」タブ）
  1. 上部に赤いバナー（例: `2件のエラー`＋行ごとの理由）
  2. 該当行を淡赤背景でハイライト
  3. 件数はサマリーボックスのエラー枠に出る（①〜③にも存在する）
- **行内に編集系のアクションは設けない（2026-07-31 確定）**
  - エラー行は**取り込まず**、`⬇ エラー行をCSVでダウンロード` で落として直し、**再アップロード**させる。書式は §9.2 の失敗行CSVと同一（元テンプレートと同じ列＋末尾に理由列・BOM付きUTF-8）で、**同じ仕組みを使い回す**
  - ファイル名は `{元テンプレート名}_エラー行_{YYYYMMDD}.tsv`
  - ボタンの位置は**プレビュー画面のフッター**、「エラー行を除いてインポート実行」の**左隣**（実装: `renderErrorCsvButtons()` / `downloadErrorRowsCsv()`。先行実装の対象は `s-tpl2` / `s-tpl2-single` の2画面）
  - 当初「行内3択アクション（マスタに追加／行編集／スキップ）」と記載していたが、**これは外部勤怠側の `s-saas-preview-single` を実装例として誤って引用したもの**。テンプレート側のモックには最初から存在しない。**先行実装では不要**（→ §0.2）
  - 画面で直させると、プレビューが編集画面になり状態管理が跳ね上がる（編集前後のデータ保持、マスタ追加後の全行再判定、エラー種別ごとの分岐）。加えて**画面で直した内容は元CSVに残らない**ため、次回の取り込みで同じエラーが再発する
- **④⑤のタブは実装では実際にフィルタさせること。** モックが表示のみなのは静的HTMLの制約であって仕様ではない。エラータブの存在価値は問題行に即座に飛べることであり、押せないタブは機能を失うだけでなく、押せると思った利用者に不信感を与える。`すべて` / `エラー` / `差し替え` / `スキップ` の全てを実フィルタにする
- 将来、店舗が数百件などでステータス絞り込みが必要になった場合も、**種別タブを主軸のまま**、表の上に「エラーのみ表示」チップを副次的に置く。タブ行には足さない

**サマリーボックスの並び順（全タブ共通）**

`[データ行数] → [新規] → [更新／権限付与] → [差し替え] → [スキップ] → [エラー]`

左端に「データ行数」、右端に「エラー」を固定する。分岐数がタブごとに違うためボックスの個数は揃わないが、並び順と色は統一する。

**色トークン（同じ意味には同じ色を全タブで使う）**

- 新規: 文字 `#0e9077` / 背景 `#e8f8f5`（緑）
- 更新・権限付与: 文字 `#5c4dac` / 背景 `#ede7f6`（紫）

- エラー: 文字 `#c62828` / 背景 `#ffebee`（赤）

**各タブ上部の説明メッセージ（確定文言）**

「何を・何件・どう処理するか」の順に統一する。

- 設定マスタ系: `①〜③ 設定マスタ: 5行を検出し、業態 2件／店舗 2件／雇用区分 3件 に仕分けました。重複は自動で除外されます。`

### 7.3 テンプレート②の営業時間

> **適用範囲: テンプレートのみ（先行実装）** — テンプレート②の列定義。外部勤怠の営業時間の扱いは後続フェーズで決定

「開店時間」「閉店時間」の2列を **「営業時間」1列**に統合する。

- 根拠: アプリ側は `stores.business_hours` を **text型の単一カラム**として持つ（`src/db/migrations/0009_stores_business_hours.sql`）。店舗登録モーダルの入力欄も単一の「営業時間」
- 推奨フォーマット: `11:00〜23:00`（24時間表記・全角チルダ区切り）。text型で自由入力のため、バリデーションではなく入力ガイドと placeholder で誘導する
- 打刻の日跨ぎ判定は v3.0 で「閉店時間+2時間」ロジックを撤廃済みのため、営業時間を自由文字列にしても打刻ロジックへの影響はない

**開発側への申し送り**

- `main` / `develop` の `POST/PUT /api/stores` は `closingTime`（HH:mm、default `"22:00"`）をZodで受けているが、`stores` テーブルに `closing_time` 列は存在しない（`tables.ts` にも全マイグレーションにも無し）。受け取って捨てている状態なので `business_hours` に一本化する
- `feature/189` の入力欄 placeholder が「開店 例:11:00」のままなので `例: 11:00〜23:00` に変更する

### 7.4 テンプレート⑤の「権限」列

> **適用範囲: テンプレートのみ（先行実装）** — テンプレート⑤の列定義

**「権限」列は削除する。** 管理者テンプレート＝管理者(manager)登録専用と位置づける。

管理者テンプレートからオーナーは登録できない。根拠は次の3点。

- 管理者登録API `POST /api/v1/administrators` の bodyスキーマ（`src/lib/schemas/administrator-body.ts`）に role／権限のフィールドが存在せず、作成されるロールは常に `manager` 固定
- `owner` はセルフサインアップ時にのみ生成される（`src/app/api/auth/sync-current-user/route.ts`：同一メールドメインの会社が未登録、かつ `userType = owner` のときにのみ会社レコードを作成）
- 会社はメールドメインで一意のため、1社1オーナー前提。オーナーを後から追加・移譲するAPIは現状ない

オーナーをテンプレートから登録する要件が出た場合は、API・DB・オーナー移譲の仕様追加が必要になるため別途検討する。

### 7.5 取込CSVの上限

> **適用範囲: 両方式共通** — 同じ登録APIを叩くため上限の根拠は共通。行数はテンプレートの種別基準で出し分ける

**①業態・②店舗・③雇用区分・⑤管理者は500行、④従業員は200行**（ヘッダー行を除いたデータ行数）。ファイルサイズ上限 **5MB** を全テンプレート共通で併用する。

> ④のみ200行なのは1行あたり最大3リクエストになるため（→ 本節末尾の追記・§8.2）。当初は「全テンプレート一律500行」としていたが、2026-07-28 に④のみ引き下げた。

上限を設ける理由はサーバー負荷そのものより、次の3点。

- **トランザクションが使えない** — `neon-http` ドライバは `db.transaction()` 非対応。途中で失敗してもロールバックできず「半分だけ入った」状態になる。バッチが長いほどリスクが増大する
- **④従業員は1行につき最大3リクエスト、⑤管理者は1行につきClerk招待APIの呼び出しが発生する** — 外部APIのレート制限が実質的なボトルネック（`src/lib/clerk-errors.ts` で 429 / `retry_after_seconds` をハンドリング済み）。DB挿入速度の問題ではない。④の内訳は「作成＋Clerk招待」「交通費」「（複数店舗時）店舗割当」→ §8.2
- **Vercelの関数実行時間上限** — `vercel.json` の `functions` にインポートAPIの `maxDuration` 指定がないためデフォルト値が適用される。同期処理で数百件の外部API呼び出しは危険

**細部**

- 判定はヘッダー行を除いたデータ行数で行う
- アップロード直後（プレビュー生成前）に弾く。パース後だと重い処理が先に走ってしまうため
- ファイルサイズ上限5MBは、1行が極端に長いCSVでのメモリ枯渇に対する保険
- ⑤管理者は招待APIがボトルネックのため、実装上500行が厳しければ100行まで下げてよい
- 500行を超える要件が出た場合は同期処理ではなく非同期ジョブ化が前提。その時点で仕様を再検討する

> **2026-07-28 追記**: ④従業員のみ上限を**200行**とする。⚠️ **これは「手入力経路の登録処理を再利用する」場合の値**（§0.7・§11）。その場合1行あたり2〜3リクエストになり、500行では最大1,500リクエストに達するため（§8.2）。**DBへ直接書く実装を選ぶ場合、この制限は不要で500行のままでよい。** 200という数字自体も暫定値で、性能実測にもとづくものではない。他テンプレートは500行のまま。`POST /api/employees` が交通費まで受け取れるよう拡張された場合は、④も500行に戻してよい。
>
> エラー文言（④従業員）: `1回に取り込めるのは200行までです。ファイルを分割してから、もう一度アップロードしてください。（アップロードされたファイル: 480行）`

**エラー文言**

`1回に取り込めるのは500行までです。ファイルを分割してから、もう一度アップロードしてください。（アップロードされたファイル: 1,240行）`

### 7.6 外部連携における管理者の扱い

> **適用範囲: 外部勤怠のみ（後続実装）** — 後続フェーズの対象

**外部連携（KoT/Jobcan）では管理者を取り込まない。** 管理者は⑤管理者テンプレート、または従業員を取り込んだ後に一覧から選択して登録する。

- 根拠: 外部サービスのエクスポートには「誰が管理者か」を示す列が存在しない。`設定データインポートマッピング表.tsv` でも、管理者の「従業員を選択」「管理店舗」はいずれも **外部サービスに該当列なし** と明記。⑤管理者テンプレートも「テンプレートのみ（外部連携対象外）」
- したがって、外部連携のデータソース選択・列マッピング・プレビューから管理者を除外した。データソース選択には「管理者は外部サービスに該当列がないため取り込まない。⑤テンプレートで登録」の案内を表示する
- これは §7.4（権限列削除・role=manager固定）と同じ「ラクミー側に権限の受け皿がない」という前提の帰結

### 7.7 インポート実行時の失敗ハンドリング（2026-07-28 確定）

> **適用範囲: 両方式共通** — 登録APIとロールバック粒度は共通。ただし**失敗行CSVの書式は §9.2 のとおりテンプレート前提**で、外部勤怠の書式は後続フェーズで決定する

**ロールバックの粒度は「行単位の補償削除」。** バッチ全体は巻き戻さず、失敗した行だけをDBに残さない。

`neon-http` ドライバは `db.transaction()` 非対応でバッチ全体のトランザクションが張れない（§7.5）。この前提のもとで、粒度を次のとおり確定する。

- **成功した行はDBに残す**（バッチは巻き戻さない）
- **失敗した行はDBに残さない** — 行の処理が途中で失敗した場合、**その行がそれまでに書き込んだレコードをすべて補償削除する**
- 結果、再取り込み時に失敗分は再び「新規登録」として判定され、成功済みは「差し替え／スキップ」に判定されるため**重複は発生しない**

> 補償削除しない案（レコードを残して未完成状態にする）は不採用。再取り込み時に「差し替え」判定となり、完了画面の確定文言「失敗した行はDBに残っていません」と矛盾するため。利用者への説明を「失敗分は入っていません」で一貫させることを優先した。

**「行の処理」は1リクエストではない（2026-07-28 追記）**

**仕様として守るべきことは1つ。「失敗した行の痕跡をDBに残さない」。** 以下の3ステップの話は、**手入力経路の登録処理を再利用する場合**の具体化である（§0.7・§11）。DBへ直接書く実装なら1回の書き込みで完結し、ステップは分かれない。

④従業員は1行の取り込みが最大3ステップに分かれる（§8.2）。**行単位＝この3ステップ全体**であり、途中で失敗したら**その行を最初の状態まで戻す**。

| ステップ | 処理 | 失敗したときに補償削除する対象 |
|---|---|---|
| 1 | `POST /api/employees`（＋Clerk招待API） | なし（何も作られていない） |
| 2 | `PUT /api/employees/[id]/commuting-allowance` | ステップ1で作成した**ユーザーレコード＋店舗割当＋Clerk招待** |
| 3 | `PUT /api/employees/[id]/stores`（複数店舗時のみ） | ステップ1・2で作成した**すべて** |

- **交通費だけ未設定のユーザーを残すことは認めない。** 交通費はテンプレート④で必須★のため、未設定のまま残すと勤怠計算の前提が崩れ、画面上も不備として見えない状態になる
- **Clerk側の招待も取り消す。** ユーザーレコードだけ消してClerk招待が残ると、招待メールのリンクから入った先にアカウントが無い状態になる。補償削除は Clerk 招待の revoke まで含める
- 補償削除自体が失敗した場合は、その行を**「要手動確認」として完了画面に別枠で表示する**。失敗行テーブルに `補償削除に失敗しました。管理者にお問い合わせください` と表示し、再取り込み対象からは除外する（再取り込みすると重複するため）

> **実装上の推奨**: ステップ1の `POST /api/employees` を交通費まで受け取れるよう拡張すれば、④のリクエスト数が1/2〜1/3になり、補償削除の分岐もほぼ消える。§8.2 の「アプリ側への依頼」を先に実施すると、本節の実装量が大きく減る。ただし**本機能のリリースはこの拡張を待たない**。

**完了画面の表示（実装済み: `index.html` の tpl3 / saas4 / tpls / saasd の4画面）**

- 全件成功: `登録処理 11件すべて成功（失敗 0 件）`
- 部分成功: `10件成功 / 1件失敗（部分成功）` ＋ **失敗した行テーブル**（行／判定／名前／メール／失敗理由）＋ 再取り込みでの回収案内
- 大見出しも状態反映する（全成功=インポート完了 ／ 部分成功=一部未完了で終了）

**エラーの切り分けと文言**

| 区分 | 扱い | 文言 |
|---|---|---|
| 行単位で切り分けられる失敗 | 該当行のみ失敗。部分成功として表示 | 失敗理由を行ごとに表示（例: `招待APIの一時的な制限(429)`） |
| プレビュー後に他操作で登録された（キー衝突） | 該当行のみ失敗 | `既に登録済みのため取り込めませんでした（他の操作で登録された可能性があります）` |
| 行単位に切り分けられない障害（DB接続断・タイムアウト・5xx） | 全件失敗。部分適用なし | `取り込みに失敗しました。データは1件も登録されていません。時間をおいてもう一度お試しください。` |

**汎用メッセージ（「CSVのインポートに失敗しました」＋リトライ促し）は使わない。** バッチを巻き戻せない以上、成功分がDBに入ったまま全件やり直しを促すことになり、二重登録の原因になる。行単位の成否開示を必須とする。

キー衝突判定に使うユニークキーは §4.3 のとおり（**必ず `companyId` で絞って突合する**）。

> 実行ボタン押下時にキー突合を再実行して判定を更新すれば、プレビューと実行のズレ（TOCTOU）の窓は縮む。ただし窓は消えないため、上記の行単位ハンドリングは必須。

**失敗行の回収手段（2026-07-28 追記・必須）**

完了画面に **「失敗した行をCSVでダウンロード」** を置く。これが無いと本節の「再取り込みで回収できます」が成立しない（500行中50行失敗した場合、ユーザーは画面の表を見ながら元CSVから手で行を拾うことになる）。

- 書式は**元テンプレートと同一列＋末尾に「失敗理由」列**を追加したもの。そのまま修正して再アップロードできる形にする
- ファイル名は `{元テンプレート名}_失敗行_{YYYYMMDD}.tsv`（テンプレートがタブ区切りのため `.tsv`）
- 「要手動確認」（補償削除に失敗した行）はこのCSVに**含めない**。再取り込みすると重複するため、別枠で表示するに留める

画面の実装は §9.2。

## 8. 実装との突き合わせで確定した事項（2026-07-28）

テンプレート列定義をアプリ側実装と突き合わせて検出した、**仕様が未確定または実装と矛盾していた項目**。全10件について決定済み。各項の「**決定**」が確定仕様、「**アプリ側への依頼**」はタイムレコード本体リポジトリ側の作業。

> **照合基準ブランチ: `rakmy/rakmytimerecord` の `origin/feature/189`**（最終コミット 2026-07-10）。
> §7 と同じ基準。`main`（2026-07-13）および `develop` には `feature/189` が**未マージ**で、`stores.business_hours`（`0009_stores_business_hours.sql`）などが存在しない。**`main` と照合すると §7.3 が誤りに見える**ため、確認時は必ずブランチを合わせること。

### 8.1 【重大】従業員コード・雇用区分コードの UNIQUE が全社横断

> **適用範囲: 両方式共通** — DB制約に起因するため突合スコープと採番規則は共通。**「配布テンプレートのサンプル行を空欄化」はテンプレートのみ**の対処で、外部勤怠は取込元CSVにコード列がある場合の扱いを後続フェーズで決定する

```sql
-- src/db/migrations/0000_smart_redwing.sql:105, 188
CONSTRAINT "employment_types_employee_code_unique" UNIQUE("employee_code")
CONSTRAINT "users_employee_code_unique" UNIQUE("employee_code")
```

`company_id` との複合ではなくテーブル全体でのユニーク。`feature/189` でも同様で、複合ユニークインデックスは存在しない。製品側も既知課題として認識（`MULTI_COMPANY_IMPLEMENTATION_STATUS.md` の Known Issues「Employee Code Uniqueness — Currently unique globally (across all companies)」）。

インポートへの影響は3点。

- **配布テンプレートのサンプル値がそのまま衝突する** — `③雇用区分.tsv` は `EMP-TYPE-001`〜`003`、`④従業員.tsv` は `EMP-001` `EMP-003` を実データ行として持つ。顧客がサンプル行を消さずに取り込むと2社目以降が必ず失敗する
- **突合スコープが未記載** — §7.1 はメールについて「必ず `companyId` で絞る」と明記しているが、§4.3 のユニークキーにはスコープの記載がない。全社横断で突合すると他社レコードを掴んで上書きする
- **自動生成の採番規則が未定義** — テンプレート③④の「空欄時は自動生成」に規則がない。全社ユニーク前提の採番（会社プレフィックス等）と衝突時のリトライ規則が要る

**決定**

1. **突合は必ず `companyId` で絞る。** §4.3 に明記済み。全社横断で突合してはならない
2. **配布テンプレートのサンプル行はコードを空欄にする。** 実施済み（`③雇用区分.tsv` / `④従業員.tsv` / `index.html` のテンプレDL生成関数）。テンプレートの備考も「空欄推奨（自動生成）」に変更済み（§1.2）
3. **自動採番はアプリ側に既存の実装がある。インポートで独自の規則を作らない**

   ```ts
   // src/app/api/employees/route.ts:286-303
   if (!employeeCode) {
       const randomNum = Math.floor(10000 + Math.random() * 90000);
       employeeCode = `EMP-${randomNum}`;            // EMP-12345（5桁ランダム）
       // 衝突していたら引き直す（while ループ）
   }
   ```

   従業員コードは **`EMP-{5桁のランダム数字}`** を生成し、衝突したら再生成する。インポートでも `employeeCode` を空で渡し、**この既存実装に採番を任せる**。
   > ⚠️ 雇用区分コード（`employment_types.employee_code`）側に同等の自動採番があるかは**未確認**。無い場合は実装が必要。実装前に確認すること。

4. **衝突時のエラー文言**（他社での使用中であることは開示しない）
   > `このコードは使用できません。別のコードを指定するか、空欄にして自動採番をご利用ください。`

5. **モックのプレビュー表に注記を置く**（表示されているコードが顧客の指定値ではなく自動採番値であることを示す）。実装は `renderAutoCodeNotes()` による注入で、`PREVIEW_SCREENS`（`s-tpl2` / `s-tpl2-single` / `s-saas-preview` / `s-saas-preview-single`）の**4画面すべて**に配る

**アプリ側への依頼（優先度高・不具合）**: **自動採番の衝突チェックが会社内に絞られている。** `src/app/api/employees/route.ts:293,300` の `getUserCompanyFilter(user.companyId)` により会社内しか確認しておらず、**他社のコードと衝突した場合はチェックをすり抜けてDB制約違反になる**（制約は全社ユニーク）。会社フィルタを外すか、複合ユニークへの移行で解消する。インポート機能は1行あたり最大3リクエストを連続で投げるため、この不具合を踏む確率が画面操作より高い。

**アプリ側への依頼**: 中期的に `(company_id, employee_code)` の複合ユニークへ移行する。移行後は上記3の会社識別子プレフィックスが不要になるため、採番規則を単純な連番に戻せる。本インポート機能のリリースはこの移行を待たない。

### 8.2 【重大】従業員1件の取込に最大3回のAPI呼び出しが必要（§7.5 の上限根拠に影響）

> **適用範囲: 両方式共通** — `POST /api/employees` は両方式が使う。上限行数もどちらにも適用する

> ⚠️ **本節は「手入力経路の登録処理を再利用する」場合の話**（§0.7・§11）。DBへ直接書く実装を選ぶ場合、リクエスト数の問題は生じず、上限行数の引き下げも不要になる。

`createEmployeeSchema`（`src/lib/api/validation.ts:47-55`）が受け取るのは次の7項目のみ。

```
clerkUserId / employeeCode / name / email / phone / employmentTypeId / storeId
```

**交通費（交通費単位・交通費）のフィールドが無い。** `POST /api/employees` は `commutingAllowances` に書き込まず（同ファイル内の参照はいずれも GET 側の一覧生成）、専用エンドポイント `PUT /api/employees/[id]/commuting-allowance` が別に存在する。

テンプレート④は交通費単位・交通費とも**必須★**のため、1行あたり次の呼び出しが要る。

1. `POST /api/employees`（＋Clerk招待API）
2. `PUT /api/employees/[id]/commuting-allowance`
3. 複数店舗の場合はさらに `PUT /api/employees/[id]/stores`（→ §8.3）

§7.5 は上限500行の根拠を「1行につきClerk招待APIの呼び出しが発生する」としているが、実際の外部・内部リクエスト数は**1行あたり2〜3倍**になる。Vercel の `maxDuration` 見積もりと上限行数の再検討が要る。

**新規登録だけでなく「上書き更新」も同じ構造。** `updateEmployeeSchema` も店舗・交通費を受け取らないため、更新時も `PUT /api/employees/[id]` ＋ 交通費 ＋ 店舗割当の最大3リクエストになる（§4.3）。上限行数の根拠は新規・更新の両方に当てはまる。

**決定**

1. **④従業員のみ上限を200行に下げる。** 他テンプレートは500行のまま（§7.5 に反映済み）
2. **現行API構成のままで実装できる仕様にする。** `POST /api/employees` の拡張を前提にしない
3. **失敗時のロールバックは §7.7 で3ステップ全体を1単位として定義済み。** 途中失敗はその行の全レコードを補償削除する（Clerk招待の revoke を含む）

**アプリ側への依頼（任意・優先度中）**: `POST /api/employees` が交通費（`交通費単位` / `交通費`）まで受け取れるよう `createEmployeeSchema` を拡張する。実現すれば ④のリクエスト数が 1/2〜1/3 になり、§7.7 の補償削除の分岐もほぼ消え、上限も500行に戻せる。**インポート機能のリリースはこの拡張を待たない。**

> §7.7 の「行単位の補償削除」は、この多段呼び出しを前提に範囲を定義し直す必要がある。従業員レコードは作れたが交通費の登録で失敗した行を、補償削除するのか交通費だけ未設定で残すのか。

### 8.3 複数店舗勤務の従業員をテンプレートで表現できない

> **適用範囲: テンプレートのみ（先行実装）** — テンプレート④の列定義。外部勤怠でマッピングした店舗列が複数店舗を持つ場合の扱いは後続フェーズで決定

アプリ側は従業員の複数店舗所属をサポートしている。

- `userStoreAssignments` は複合主キー `(user_id, store_id)` の多対多（`src/db/schema/tables.ts:179-195`）
- 従業員一覧は `assignedStores` を配列で返す（`src/app/api/employees/route.ts:200`）
- 割当専用エンドポイント `PUT /api/employees/[id]/stores` は `storeIds` を**配列**で受ける（`src/app/api/employees/[id]/stores/route.ts:99-106`）

一方、`createEmployeeSchema` の `storeId` は**単一**、テンプレート④の「店舗名」も**単一値**。⑤管理者テンプレートの「担当店舗」は「複数指定は半角カンマ区切り」と明記されており、④との非対称が意図的かどうか不明。

**決定**

**④従業員の店舗名は単一のままとする。** 複数店舗勤務は取り込み後に従業員一覧の画面から追加する運用。テンプレート備考に明記済み（§1.2）。

④と⑤の非対称は**意図的なものとして確定**する。理由は両者で「店舗」の意味が違うため。

- ⑤管理者の「担当店舗」＝**権限の範囲**。初期登録の時点で確定していないと、その管理者が何も操作できない
- ④従業員の「店舗名」＝**主たる勤務先**。複数店舗勤務は例外的で、初期一括登録の時点では未確定なことが多い

⑤は初期取込で複数指定が必須、④は後追いで足りる。この差をヘルプにも記載する。

> 完了画面の「次にやること」に「複数店舗で勤務する従業員がいる場合は、従業員一覧から所属店舗を追加してください」を追加する。

### 8.4 「月みなし残業時間」の保存先がカラム名と乖離している（`shift_restriction` / text型）

> **適用範囲: 両方式共通** — 格納先カラムが同じため

`employmentTypes.shiftRestriction`（`text`）に月みなし残業時間を格納している。独立した2つの箇所で確認できる。

- `src/app/dashboard/employment/page.tsx:498` — `<Table.Head id="shiftRestriction" label="月みなし残業時間" />`
- `src/lib/api/export-utils.ts:57,71` — `{ label: "月みなし残業時間", value: "overtimeHours" }` / `overtimeHours: employee.employmentType?.shiftRestriction`

型が `text` のため数値バリデーションが完全にアプリ側任せで、`3時間` `約20` のような文字列がそのまま入る。なお「月次契約労働時間」は `contractHours`（`integer`）で型は正しい（同 page.tsx:497 で `breakRule` として表示、export-utils.ts:56 で `contractHours`）。

**決定**

1. **マッピングを明記する**: `月みなし残業時間 → employment_types.shift_restriction`（text型）。カラム名と意味が乖離しているため、マッピング表と本節の両方に残す
2. **インポート時に数値バリデーションを行う**（アプリ側が text で受けるため、取り込み側で担保する）
   - 許可: 0以上999以下の整数。単位（`時間`）は含めない
     > ⚠️ **上限999は暫定値**（設計判断）。アプリ側に既存の範囲制約は無く、数値であること以外の根拠はない。実運用でこれを超える値が出れば見直す
     > **月みなし残業時間は0を許す**（0＝みなし残業なし、として意味を持つため）。実装は `shiftRestriction` が text型で範囲制約を持たない。**月次契約労働時間（`contractHours`）とは別列**で、そちらは実装が0を受け付けないため1以上（下記3）
   - 空欄可（`contract_hours` と同じく任意項目）
   - エラー文言: `月みなし残業時間は0〜999の半角数字で入力してください。（入力値: 3時間）`
3. 同様に **月次契約労働時間 → `employment_types.contract_hours`**（integer）も明記する。範囲は **1以上999以下**
   > 実装が `contractHours: z.number().int().positive()` で**0を受け付けない**（`src/app/api/employment-types/route.ts`）。月0時間の契約は存在しないため**この制約は正しく、実装は変更しない**。当初「0〜999」と記載していたのは誤りで、実装に合わせて訂正した（2026-07-28）
   > エラー文言: `月次契約労働時間は1〜999の半角数字で入力してください。（入力値: 0）`

**アプリ側への依頼（優先度低）**: `shift_restriction` を `deemed_overtime_hours`（integer）へリネーム＋型変更する。カラム名から用途が読めず、将来の担当者が必ず誤解する。インポート機能のリリースはこれを待たない。

### 8.5 業態名・店舗名に UNIQUE 制約がない

> **適用範囲: 両方式共通** — DB制約と突合ロジックに起因するため

§4.3 のユニークキーは「店舗＝店舗名」「業態＝業態名」だが、DB側に裏付けがない。

- `business_types.label` — `varchar(100) NOT NULL`、UNIQUE なし
- `stores.name` — `varchar(255) NOT NULL`、UNIQUE なし（インデックスは `business_type_id` と `company_id` のみ）

§7.2 の確定文言「重複は自動で除外されます」を成立させるには、アプリ側で突合する実装指定が要る。

**決定**

1. **突合は「会社内・名称の完全一致」**。前後の空白のみトリムする。全角半角・大文字小文字の正規化は**行わない**（`ABC店` と `ＡＢＣ店` を同一視すると、意図的に使い分けている顧客のデータを壊すため）
   > ⚠️ **設計判断**。アプリ側に既存の名称突合ロジックは確認していない。既存実装がある場合はそちらに合わせること
2. **CSV内の重複は取り込み前に自動除外する**（§7.2 の確定文言「重複は自動で除外されます」どおり）。同一ファイル内に同名の業態・店舗が複数行ある場合は先頭行を採用し、2行目以降は「スキップ」として扱う
3. **DB側に既に同名が複数ある場合はその行をエラーにする**
   > `同名の店舗が複数登録されているため、どちらに紐づけるか判断できません。店舗一覧で整理してから取り込んでください。（店舗名: 渋谷店）`

**アプリ側への依頼（優先度中）**: `business_types.label` と `stores.name` に `(company_id, name)` の複合ユニークを追加する。上記3のエラーは、制約が無いことに起因する後始末であり、本来は入口で防ぐべきもの。

### 8.6 雇用区分のユニークキー「コード or 名」の or

> **適用範囲: 両方式共通** — 突合ロジックに起因するため

§4.3 は「雇用区分: 雇用区分コード or 雇用区分名」とあったが、コードが空欄の行を名前で突合するのか、その場合に同名が複数あったらどうするのかが未定義だった。DB上 `employment_types.name` に UNIQUE はないため、この分岐は必ず発生する。

**決定：優先順位を明示する。**

1. **雇用区分コードが入力されていればコードで突合する**（名前は見ない。名前だけ変更するリネーム運用を成立させるため）
2. **コードが空欄なら雇用区分名で突合する**
3. **名前で突合して会社内に複数一致した場合はエラー**にする。§8.5 の店舗・業態と同じ扱い
   > `同名の雇用区分が複数登録されているため、どれに紐づけるか判断できません。雇用区分コードを指定するか、雇用区分一覧で整理してから取り込んでください。（雇用区分名: パートB）`
4. コードも名前も一致しなければ**新規登録**

§4.3 のユニークキー表記を「雇用区分コード（空欄時は雇用区分名）」に変更済み。

### 8.7 CSVの空欄セルの意味

> **適用範囲: 両方式共通** — CSVの性質に起因するため

§4.3 は「スキップ／上書き更新」をレコード単位で定義しているのみで、**列単位の意味がなかった**。上書き更新を選んだとき、CSVで空欄の列を「変更しない」とするか「NULLで上書き」とするかが未定義だった。

**決定：空欄の列は「変更しない」。NULLで上書きはしない。** §4.3 に明記済み。

モックの「重複時の処理」UI3箇所すべてに次の注記を追加した。
> `「上書き更新」を選んだ場合も、CSVで空欄の列は変更されません（空欄で既存の値が消えることはありません）。値を消したい場合は、取り込み後に各設定画面から編集してください。`

- CSVは空文字とNULLを区別できないため、「空欄＝消去」にすると、列を削って作った部分更新用CSVがデータを消す事故になる。しかも不可逆
- 値を消したい場合は画面から編集する。この旨をヘルプに記載する
- **例外なし**。必須★の列が空欄の行は「変更しない」ではなく**エラー**として扱う（新規登録の場合は必須項目不足、更新の場合も同様にエラー）

### 8.8 列ごとのバリデーションが未定義

> **適用範囲: 両方式共通** — 実効上限はAPIスキーマに起因する。表の列名はテンプレート基準だが、外部勤怠ではマッピング後の値に同じ検証を適用する

§7.5 に全体の上限（500行・5MB）はあるが、列単位の制限が仕様書に一切ない。アプリ側の実際の制約は次のとおりで、**DBの桁とAPIスキーマで上限が異なる列がある**。

| テンプレート列 | DB | APIスキーマ | 実効上限 |
|---|---|---|---|
| 従業員名 | `varchar(255)` | `z.string().min(1).max(100)` | **100** |
| 従業員コード | `varchar(50)` | `z.string().max(50).optional()` | 50 |
| メールアドレス | `varchar(255)` | `z.string().email()` | 255 |
| 電話番号 | `varchar(20)` | `regex(/^[0-9\-\+\(\)\s]+$/)`・**`.optional()`** | 20 |
| 雇用区分名 | `varchar(100)` | — | 100 |
| 雇用区分コード | `varchar(50)` | — | 50 |
| 業態名 | `varchar(100)` | — | 100 |
| 店舗名 | `varchar(255)` | — | 255 |
| 金額 | `decimal(10,2)` | — | 99,999,999.99 |

**決定**

0. **モックへの反映**: アップロードボックスの表記は種別ごとに出し分ける（`rowLimitOf()`）。①②③⑤は「最大500行・5MB」、④従業員は「最大200行・5MB」。一括アップロード画面と外部勤怠画面は複数種別を扱うため「最大500行・5MB／④従業員は200行」と併記する
1. **上記表の「実効上限」を取り込み時のバリデーション値とする。** ⚠️ **ただし「実効上限」は手入力経路の zod スキーマ由来**（§0.7）。**DBへ直接書く実装を選ぶ場合はDBの桁が上限**になる（従業員名は100ではなく255）。どちらを採るかは §11 の決定に従う
2. **超過時のエラー文言**（列名と上限を必ず出す）
   > `従業員名は100文字以内で入力してください。（行3・入力値: 105文字）`
3. **金額列の正規化**（⚠️ **設計判断**。アプリ側に既存の正規化処理は確認していない）: 取り込み時に次を正規化してから検証する。正規化しても数値にならない場合はエラー
   - 全角数字 → 半角に変換
   - カンマ（`,` `，`）→ 除去
   - 円記号（`¥` `￥` `円`）→ 除去
   - 前後の空白 → トリム
   - エラー文言: `金額は半角数字で入力してください。（行3・入力値: 二十万円）`
4. **電話番号はテンプレート側の必須★に合わせる**（取り込み時は必須）。⚠️ **アプリ側の `phoneSchema` は `.optional()` で任意。インポートだけ厳しくする設計判断**。理由は打刻トラブル時の連絡手段として運用上不可欠であり、後から一括で集めるのが困難なため。API側が `.optional()` なのは画面登録との互換のためで、そちらは変更しない
   - 形式は `phoneSchema` と同じ `^[0-9\-\+\(\)\s]+$` を採用し、20文字以内
   - エラー文言: `電話番号は半角数字とハイフンで入力してください。（行3・入力値: 090ー1234ー5678）`

> 全角ハイフン（`ー`）の混入はExcel入力で頻発するため、**ハイフン類（`ー` `－` `‐` `–`）は半角 `-` に正規化してから検証する**。

### 8.9 退職者・無効レコードとの突合

> **適用範囲: 両方式共通** — 突合ロジックに起因するため

`userStatusEnum` は `["active", "inactive", "retired", "inviting"]`（`src/db/schema/enums.ts`）。退職済み（`retired`）の従業員と同じ従業員コードで取り込んだ場合の扱いを定める。§8.1 のとおりコードは全社ユニークのため、この行は必ず衝突する。

**決定**

**退職者（`retired`）・無効（`inactive`）と同じ従業員コードの行は「エラー」とし、取り込まない。** 自動で復活させない。

- 再雇用は在籍期間・雇用条件が変わるため、CSVの1行で暗黙に復活させると勤怠・給与の履歴が壊れる（`employment_type_history` は `(user_id, effective_date)` でユニーク）
- 判定ラベルは「エラー」、行内アクションは「⊘ スキップ」のみを出す（「マスタに追加」「行編集」は無意味なため出さない）
- エラー文言:
  > `退職済みの従業員と同じ従業員コードです。再雇用の場合は従業員一覧から復帰の手続きを行ってください。（従業員コード: EMP-3f2a91c7-0007）`
- `inviting`（招待済み・未承諾）は**エラーではない**。⑤管理者の「差し替え」と同じ扱いで、招待を再発行する

モックの④従業員プレビューに該当行を追加済み（`data-err-type="retired"`）。

### 8.10 給与体系の「日給」（削除・対応済み）

> **適用範囲: 両方式共通** — DBのenumに起因するため。マッピング表も修正済み

モック・テンプレート・入力ガイド・マッピング表は「月給 / 日給 / 時給」の3値だが、アプリ側は2値。

```
src/db/schema/enums.ts:8
pgEnum("employment_category", ["時給", "月給"])   // feature/189 でも同じ
```

`src/app/api/employee/profile/route.ts:86,197` が `category === "時給" ? "hourly" : "monthly"` と else 分岐で処理しているため、日給を追加してもエラーにならず**サイレントに月給として計算される**。連携先の経営管理も「給与.日給月給制／給与.時給制」の2区分で、日給月給制は月給の一種であり日給ではない（§2.2）。

また `③雇用区分.tsv` の `日給スタッフC EMP-TYPE-003 日給 10000 8` は、末尾の `8` が「月次契約労働時間」の列に入っており、1日の所定労働時間を誤って置いたものと見られる。仕様が詰まらないまま列だけ埋まっていた形跡。

**決定：日給を削除し「月給 / 時給」の2値に統一する。対応済み。**

| ファイル | 変更内容 |
|---|---|
| `README.md` §1.2 ③ | 給与体系の許可値を `月給 / 時給` に |
| `入力ガイドv2.tsv` | 同上 |
| `設定データインポートマッピング表.tsv` | 同上 |
| `③雇用区分.tsv` | サンプル行 `日給スタッフC / 日給 / 10000 / 8` → `アルバイトC / 時給 / 1100 / 空欄` |
| `④従業員.tsv` | 高橋美咲の雇用区分名を `アルバイトC` に |
| `index.html` | 給与体系の `options` 配列、エラー行の許可値表示、プレビュー行7箇所、テンプレDL生成関数 |

> **経営管理側のマッピング先（`給与.日給月給制` / `給与.日給制`）は変更しない。** これは経営管理のフィールド名であり、タイムレコードの給与体系とは別物。「日給月給制」は欠勤時に日割り控除する月給制のことで、日給ではない。

日給払いの顧客が現れた場合は、enum のマイグレーション・給与計算・経営管理側の受け皿設計を含む**別案件として起票**する。本インポート機能のスコープには入れない。

### 9.1 【重大】取り込み実行中の状態（実装済み）

> **適用範囲: 両方式共通** — 画面挙動として共通

進捗表示・スピナー・実行中の画面が一切ない。§8.2 のとおり従業員は1行あたり2〜3リクエスト（＋Clerk招待API）が発生するため、500行では数十秒〜数分かかる。その間ユーザーに何も表示されない。

現行の `disabled` 制御は「必須項目未達で次へ進めない」用途のみで（`index.html:4195` `4215` `4340` `4348` `4377`）、**インポート実行ボタンの二重押下防止が存在しない**。連打すれば取り込みが多重実行される。

**決定**（実装: `#import-running-overlay` / `runImport()`）

1. **実行中はモーダルオーバーレイを表示する。** スピナー＋プログレスバー＋`n / N 件` のカウンタ。ラベルは処理中の種別（`従業員 を登録中…`）
2. **実行ボタンは押下と同時に `disabled` にする。** グローバルフラグ `_importRunning` でも二重実行を防ぐ（連打・別画面からの再入の両方を塞ぐ）
3. **実行中は `beforeunload` で離脱を警告する**

4. **中断時の説明をオーバーレイ内に常時表示する**

> **実装時の注意**: モックは擬似進捗（一定間隔でカウントアップ）だが、**実装ではサーバーから返る実際の処理済み件数で更新すること**。§8.2 のとおり④従業員は1行あたり最大3リクエストのため、リクエスト単位ではなく**行単位**でカウントする。

### 9.2 【重大】失敗行のCSVダウンロード動線（実装済み）

> **適用範囲: テンプレートのみ（先行実装）** — **書式が「元テンプレートと同一列」のためテンプレート前提。** 外部勤怠は列マッピングを経るため「元テンプレート」が存在せず、取込元CSVの列で出すのかマッピング後のラクミー列で出すのかを**後続フェーズで決定する**

デモは失敗1件なので手作業で足りるが、500行中50行が失敗した場合、ユーザーは完了画面の表を見ながら元CSVから該当行を手で拾う必要があり、実運用では成立しない。ダウンロード動線はテンプレートDL（`:1093`〜`:1131`）と補完用テンプレートDL（`:2644`）のみで、エラー行の書き出しは存在しない。

**§7.7 の「再取り込みで回収できます」は、この動線がなければ画餅になる。**

**決定**（実装: `downloadFailedRowsCsv()`）

> **先行実装の対象は完了画面2箇所**（`s-tpl3` / `s-tpl3-single`）。モックは外部勤怠側（`s-saas4` / `s-saas-done-single`）にも配置しているが、そちらは**後続フェーズの参照用**で、書式は後続フェーズで決定する（→ §10-1）。

1. **完了画面の部分成功ブロックに「⬇ 失敗した行をCSVでダウンロード」を置く。** 失敗行テーブルの直下
2. **書式は元テンプレートと同一列＋末尾に「失敗理由」列。** そのまま修正して再アップロードできる形にする
3. **ファイル名**: `{元テンプレート名}_失敗行_{YYYYMMDD}.tsv`（テンプレートがタブ区切りのため `.tsv`）
4. **「要手動確認」（補償削除に失敗した行）はこのCSVに含めない。** 再取り込みすると重複するため（§7.7）

**あわせて完了画面に「次にやること」を置く（§8.3）**: 複数店舗勤務の従業員は取込後に従業員一覧から所属店舗を追加する旨、およびコードを空欄にした行は自動採番された旨を案内する。実装は `renderNextStepsBlocks()` による注入で、`COMPLETE_SCREENS`（`s-tpl3` / `s-saas4` / `s-tpl3-single` / `s-saas-done-single`）の**4画面すべて**に配る。

### 9.3 上限超過の受付拒否（実装済み）

> **適用範囲: 両方式共通** — 画面挙動として共通

`index.html:1169-1176` は「取込上限」の**仕様メモ枠**で、エラー文言は見本として静的に置かれているだけ。実際に501行以上・5MB超のファイルをアップロードしたときの遷移がない。

§7.5 は「アップロード直後（プレビュー生成前）に弾く」と定めているため、**プレビューへ進まずアップロード画面に留まる**状態が要る。

**決定**（実装: `demoUploadReject('rows'|'size')` / バナーは `.upload-reject-box` としてアクティブ画面に動的注入）

1. **アップロード画面上に赤い受付拒否ボックスを出す。** プレビューへは進ませず、**アップロード済みファイル一覧にも追加しない**
2. **復帰導線は「閉じる」のみ。** ファイルを直して再度アップロードしてもらう
3. **エラー文言**
   > 一括取込画面（複数種別）: `1回に取り込めるのは500行までです。ファイルを分割してから、もう一度アップロードしてください。（アップロードされたファイル: 1,240行）` ＋ `※ ④従業員は200行までです。`
   > ①②③⑤の単体取込画面: `1回に取り込めるのは500行までです。…`（④の注釈は出さない）
   > ④従業員の単体取込画面・補完テンプレート画面: `1回に取り込めるのは200行までです。ファイルを分割してから、もう一度アップロードしてください。（アップロードされたファイル: 480行）`
   >
   > **画面の取込対象種別に応じて文言を出し分ける。** 種別は `data-single-tpl-key` / `data-single-saas-key` / `data-import-entity` 属性から判定する（`activeEntityKey()`）。一括画面のみ併記とし、種別が確定している画面で「※ ④従業員は200行」と注釈を足すことはしない
   > サイズ超過: `1ファイルあたり5MBまでです。不要な列や空行を削除するか、ファイルを分割してからアップロードしてください。（アップロードされたファイル: 8.2MB）`

### 9.4 全件エラー（取り込める行が0件）の状態（実装済み）

> **適用範囲: 両方式共通** — 画面挙動として共通

「エラー行を除いてインポート実行」ボタン（`index.html:1419` / `2391`）は常に押せる前提で作られている。全行がエラーの場合、0件で実行されて完了画面に進む。

**決定**（実装: `demoZeroTarget()` / 理由ボックスは `.zero-target-box` としてアクティブ画面に動的注入）

1. **取り込み対象が0件のとき、実行ボタンを `disabled` にする。** 0件実行で完了画面へ進ませない
2. **ボタン文言には `（0件）` を表示する。** 件数を隠すと「なぜ押せないのか」が分からなくなるため
3. **プレビュー上部に赤いボックスで理由を出す**
   > `取り込めるデータが1件もありません。`
   > `すべての行にエラーがあります。エラーを解消するか、ファイルを修正してからもう一度アップロードしてください。`

### 9.5 ファイル形式エラーの状態（実装済み）

> **適用範囲: 方式別に定義済み** — テンプレートはBOM付きUTF-8配布・文字コード選択UIなし。外部勤怠は他社CSVを受けるためShift_JIS/UTF-8セレクタを維持する

次のいずれもモックに画面がない。

- **文字コード不正** — 外部勤怠側の取り込み設定には `Shift_JIS` / `UTF-8` のセレクトがある（`index.html:1856` `1886`）が、**テンプレートインポート側には文字コードの指定が一切ない**。Excel で保存した CSV は Shift_JIS が既定のため、テンプレート運用では必ず踏む
- **列名不一致** — ④従業員のテンプレートを②店舗の枠にアップロードした場合など
- **ヘッダー行なし・空ファイル・データ行0件**

**決定**（実装: `UPLOAD_REJECT_MSG` / `demoUploadReject('encoding'|'columns'|'empty')`）

1. **テンプレートDLは BOM付きUTF-8 で配布する。** Excelで開いて保存し直しても UTF-8 が維持されるため、文字コード問題の大半を入口で潰せる。テンプレート側に文字コードの選択UIは設けない（外部勤怠サービス連携側の取り込み設定にある Shift_JIS / UTF-8 セレクトは、他社CSVを受けるため必要なので現状維持）
2. **エラー文言**
   > 文字コード: `ファイルの文字コードが UTF-8 ではない可能性があります。テンプレートをダウンロードし直し、Excelで「CSV UTF-8 (コンマ区切り)」形式で保存してからアップロードしてください。`
   > 列名不一致: `このファイルには必要な列がありません。別の種別のテンプレートをアップロードしていないかご確認ください。`
   > データ0件: `ヘッダー行のみで、データ行が1件もありません。データを入力してからアップロードしてください。`
3. **列名不一致では「必要な列」と「見つかった列」を両方出す。** 種別を取り違えたことが一目で分かるようにするため

> テンプレートDLをBOM付きUTF-8で配布すれば、Excel で開いて保存し直しても UTF-8 が維持されるため、文字コード問題の大半は入口で潰せる。

### 9.6 権限（オーナー／管理者）による出し分け（実装済み）

> **適用範囲: 両方式共通** — 権限はアプリ側の実装に起因するため

モックはオーナー前提の1系統のみ。アプリ側では**管理者（manager）もインポート対象の操作を実行できる**。

```
src/lib/api/permissions.ts:29-44 (feature/189)
canManageEmploymentTypes / canCreateEmployee / canEditEmployee / canCreateManager
　→ いずれも user.role === "owner" || user.role === "manager"
```

一方、管理者は担当店舗のみが範囲という前提が owner-mock 側にある。管理者がインポートを実行した場合に、**担当店舗外の店舗名を含む行をどう扱うか**（エラーにする／無視する／そもそも画面に入れない）が未定義。

**決定**（実装: `setHubRole()` / インポートハブ `s-top` のロール切替）

1. **管理者（manager）にもインポートを開放する。** アプリ側が既に権限を与えており（`canCreateEmployee` ほか）、塞ぐ方が実装コストが高いため
   > ⚠️ **アプリ側は `canManageEmploymentTypes` / `canCreateEmployee` / `canCreateManager` のいずれも `owner || manager` で許可している。** 下記2で全社マスタをオーナー限定にするのは**インポート機能だけの制限**であり、アプリ側の権限設計を変えるものではない（画面からは管理者も操作できる）。この非対称を意図的なものとして確定する
2. **全社マスタ（①業態・②店舗・③雇用区分）はオーナー限定。** 管理者のインポートハブには表示しない。担当店舗しか範囲を持たない管理者が会社全体の設定を変更できるのは権限設計と矛盾するため
3. **④従業員・⑤管理者は管理者も取り込めるが、担当店舗の行のみ。** 担当外の店舗名を含む行は**エラー**として扱い、取り込まない
   > `担当店舗以外の従業員は取り込めません。（店舗名: 池袋店）`
4. **ハブ上部に現在のロールと範囲を常時表示する**
   > `管理者(店長)としてログイン中 — 従業員・管理者のみ、担当店舗の範囲で取り込めます`

モックの④従業員プレビューに担当店舗外のエラー行を追加済み（`data-err-type="out-of-scope"`）。

### 9.7 プレビューで除外した行を完了画面で開示する（実装済み）

> **適用範囲: 両方式共通** — 画面挙動として共通

**エラーは発生タイミングで3種類あり、表示される画面が異なる。**

| タイミング | 種類 | 表示場所 | 完了画面に出るか |
|---|---|---|---|
| ① アップロード時 | 行数超過・サイズ超過・文字コード・列名不一致・データ0件 | アップロード画面の受付拒否バナー（§9.3・§9.5） | **出ない**（プレビューに進まないため） |
| ② プレビュー時 | 値不正・マスタ未登録・退職者（§8.9）・担当店舗外（§9.6） | プレビューの行ハイライト＋エラー列 | **従来は出なかった → 本節で追加** |
| ③ 実行時 | 招待API 429・キー衝突・補償削除失敗 | 完了画面の失敗行テーブル＋失敗行CSV（§7.7・§9.2） | 出る |

**問題**: ②で除外した行が完了画面から消えていた。15行中1行がエラーの場合、「エラー行を除いてインポート実行（14件）」→ 完了画面は「登録処理 14件すべて成功」となり、**利用者は全件成功したと受け取って除外分を放置する**。③には失敗行テーブルとCSVという手厚い回収動線があるのに、②には何もなかった。テンプレート側（`s-tpl3`）と外部勤怠側（`s-saas4`）で扱いが揃っていない状態でもあった。

**決定**（実装: `renderExcludedRowsBlocks()` / 完了画面4箇所）

1. **完了画面に「取り込まなかった行 (N件) — プレビューでエラーのため除外」を常時表示する。** 行番号・対象・メール・除外理由の表付き
2. **全件成功時も表示する。** 「11件すべて成功」と「取り込まなかった行 3件」は両立する。成功件数だけを見せると①②を見落とす
3. **失敗行CSV（§9.2）に除外分も含める。** 失敗理由列に `プレビューでエラーのため除外: {理由}` と記載し、実行時の失敗と同じファイルで回収できるようにする
4. **説明文**
   > `これらの行は実行前に除外されており、登録されていません。原因を解消してから再取り込みしてください。「失敗した行をCSVでダウンロード」には、この除外分も含まれます。`

> ①のアップロード時エラーは完了画面に出さない。ファイル自体が受理されておらず、取り込みセッションが始まっていないため。

モックの④従業員プレビューに担当店舗外のエラー行を追加済み（`data-err-type="out-of-scope"`）。

## 11. エンジニアと決めること（2026-07-28 起票）

### 11.1 【最優先】インポートは手入力の登録処理を再利用するか

**登録の経路は2つ**（§0.7）。テンプレートインポート登録と、手入力設定登録（画面から1件ずつ）。**インポートが手入力の登録処理を再利用するかどうかが未決**で、この判断によって仕様の複数箇所が変わる。

| | 再利用する | DBへ直接書く |
|---|---|---|
| 業務ロジック | 招待メール送信・Clerk連携・権限付与を**そのまま使える** | **作り直すか、書き漏らす** |
| ④の1行あたりの処理回数 | 最大3回（§8.2） | 1回 |
| ④の上限行数 | **200行**（§7.5） | 500行のままでよい |
| 失敗時の巻き戻し | 3ステップ全体を1単位とする補償削除（§7.7） | 1回の書き込みなので単純 |
| 列の桁上限 | 手入力経路の zod に従う（従業員名100文字） | **DBの桁**に従う（255文字） |
| 担当店舗 | 置換されるためマージが必要（§7.1） | 消さないように書けばよい |

**現時点の仕様は「再利用する」前提で書いている。** 各所に「手入力経路を再利用する場合」と条件を明記した。

> **PdM側の見解**: 業務ロジックの再利用が効くため「再利用する」が有力と考えるが、**リクエスト数・上限行数・巻き戻しの複雑さと引き換え**になる。実装コストの見積もりを含め、エンジニアの判断を仰ぎたい。

**決まったら反映する箇所**: §7.1 ／ §7.5 ／ §7.7 ／ §8.2 ／ §8.8 ／ §4.4
